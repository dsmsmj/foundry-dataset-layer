质量检查：关卡还是报警器？

这一课只讲一个点：Data Expectations 在构建里面拦截坏数据，Data Health 检查在构建之后发现问题并告警。学完你能判断一次检查失败后，坏数据会不会进入视图。

文件→事务→视图→ 分支→构建→质量检查→Ontology→权限

每题只能答一次，先在脑子里说出答案再点。答错没关系，回忆本身就是练习。

下面哪种情况会让增量 transform 下一次强制快照运行？

  1. 把 semantic_version 从 1 改成 2
  2. 保持 semantic_version 等于 1
  3. 输入上新提交了一条 APPEND
  4. 给 transform 加上 allow_retention

  1. 照常增量，只读新增
  2. 新鲜跳过，不会运行
  3. 退回快照，全量重算
  4. 构建直接报错并失败

在 feature 上构建，链是 feature → develop → master。输出还没有 feature 分支，这个分支从哪里创建？

  1. 从 master 创建
  2. 从 develop 创建
  3. 作为根分支创建
  4. 不建，写到 develop

某输出的输入没有新事务，代码也没改。这次构建它会怎样？

  1. 全量重新计算一遍
  2. 增量只读新增部分
  3. 构建失败并报错误
  4. 被跳过，不会重算

1. 唯一的知识点（约 5 分钟）

Foundry 有两种质量检查。用一个比喻记：Expectation 是安检门，Data Health 检查是烟雾报警器。安检门在你进去之前拦人；报警器在火已经烧起来之后才响。

Data Expectations（安检门）Data Health 检查（报警器）
写在哪transform 代码里，挂在输入或输出上挂在数据集或调度上，在 Data Health 里配置
什么时候跑构建 Job 运行期间大多数检查要等 Job 结束后才计算
失败了会怎样FAIL：Job 被中止；WARN：继续跑，发一条警告只告警，不拦数据

依据：Define data expectations 原文 "The registered checks will run as part of the build job"；Data Health check types 说大多数标准检查要等 Job 结束才能计算。

为什么 FAIL 能挡住坏数据？用第 3 课和第 1 课推一下：Job 被中止 → 它在输出上开的那条事务被放弃（ABORTED）→ 第 1 课说过，ABORTED 事务写的文件被忽略 → 坏数据进不了视图，下游读到的还是上一次的好数据。

这条是由几课的规则推出来的结论，文档原文只写到"Job 状态变为 Aborted"。

还有两个小词：

  • 挂在输入上的检查叫 pre-condition（前置条件）：开工前先验收原料，失败则这个 transform 的输出被中止。
  • 挂在输出上的检查叫 post-condition（后置条件）：出厂前验收成品，保护下游。

Expectation 的结果也会上报到 Data Health 里统一看。不写 on_error 时，默认是 FAIL[调研笔记 §6.2]。

2. 分类练习（约 5 分钟）

每题描述一个检查和一次失败。判断结果是哪一种。三个选项在每题里都一样。
