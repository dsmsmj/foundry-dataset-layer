构建：什么时候重算，什么时候跳过

学完这一课，告诉你一条管道上次构建之后发生了什么变化，你能说出这次构建会重算哪些数据集、跳过哪些，以及为什么。

0. 热身：输入和输出缺分支

上一课最容易混的地方。记住那句话：输入往后退着读，输出往前建着写。

在 feature 分支上构建，fallback 链是 feature → master。输入 raw_orders 只有 master 分支。会怎样？

  1. 新建分支，然后再读取
  2. 直接报错，解析会失败
  3. 读主分支，不新建分支
  4. 作为根分支，从头构建

同一次构建，输出 clean_orders 也没有 feature 分支，只有 master。会怎样？

  1. 作为全新的根分支创建
  2. 构建失败，提示无分支
  3. 改写到主分支上的输出
  4. 从第一个后备分支创建

1. 构建、Job 与 JobSpec

"A Build is the mechanism used to compute new versions of datasets in Foundry." — Palantir Docs · Builds

"新版本"用第 1 课的话说，就是在输出数据集上提交一条新事务。一次构建由若干 Job 组成，每个 Job 是一份共享逻辑的工作单元[文档]。

  • JobSpec：一个 Job 该怎么构造的定义：读哪些输入（每个输入写成一条 InputSpec）、用什么逻辑算。修改转换逻辑时会发布新的 JobSpec[文档]。上一课的 fallback 链，解析的就是它。
  • 多输出 Job：一个 Job 有多个输出时，这些输出总是一起更新，不能只构建其中一个[文档]。

2. 一次构建的两个阶段

解析（resolution）：先把账算清

  1. 检查依赖里有没有环，有就直接失败。
  2. 检查输入都存在，并确定每个输入的 schema。
  3. 在每个输出上先开一条事务，确保只有这次构建能写它。官方叫 build locking。
  4. 如果另一个正在跑的构建会改动它的输入，这次构建可能排队等它结束。

四条都出自 Build lifecycle。

第 3 步和第 1 课直接相连：输出上的事务这时是 OPEN，Job 成功就 COMMITTED，失败就 ABORTED，写进去的文件被忽略。

解析阶段为什么要先在每个输出上开一条事务？

  1. 先占位，方便计算行数
  2. 让下游马上读到新数据
  3. 保证只有本次构建能写
  4. 记录这次构建的发起人

执行（execution）：有 Job 失败时

某个 Job 失败，直接依赖它的 Job 和输出上的事务会被终止。但要注意：已经完成的 Job 可能已经把数据写进了它们的输出[文档]。一次构建不是"要么全成、要么全不成"。

构建中 order_facts 的 Job 失败了。在它之前已经完成的 clean_orders 呢？

  1. 全部自动回滚到构建前
  2. 已写入的数据可能保留
  3. 也一起被标记为失败了
  4. 要等重试成功后才提交

3. 新鲜度：为什么会跳过

这是本课的核心。官方规则[文档 · Staleness]：

如果一个输出的输入数据集和 JobSpec 逻辑自上次构建以来都没变，它就是新鲜的（fresh），之后的构建不会重算它。

force build 例外：不管新不新鲜，全部重算。

把它和前两课连起来，就能推出一条很有用的结论：上游一旦被重算，就会提交一条新事务，它的视图变了；对下游来说，这就是"输入变了"，于是下游也不新鲜了。变化会顺着依赖往下游传。

"输入变了"在这里理解为输入有了新的已提交事务。这是从规则推出的理解，文档原文只说输入数据集没有变化。

刚构建完，什么都没改，马上再点一次构建，会怎样？

  1. 全部重算一遍再提交
  2. 报错提示没有新数据
  3. 只重算最下游的数据
  4. 输出新鲜，直接跳过
