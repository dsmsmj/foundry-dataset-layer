Ontology 不直接读数据集

这一课只讲一个点：对象（Object）的数据来自数据集，但中间隔着一个索引服务 Funnel。学完你能判断数据集发生某个变化时，对象那边会怎样。

0. 回忆热身（约 5 分钟）

为什么 Expectation 的 FAIL 能让坏数据进不了视图？

  1. 输出事务被放弃，文件不进视图
  2. 坏数据被自动回滚到上一个版本
  3. 检查器会直接删除掉那些坏文件
  4. 报警器通知人去手工撤回数据了

增量 transform 增量运行时，输出默认怎么写？

  1. 整体替换整个输出
  2. 写到一个新数据集
  3. 追加到已有输出上
  4. 只更新被改的那行

删除一个数据集分支，分支上的事务会怎样？

  1. 随着分支一起被删除
  2. 全部保留，只删指针
  3. 合并进父分支历史里
  4. 等待保留策略来清理

1. 唯一的知识点（约 5 分钟）

Ontology 把数据变成业务"对象"：一个订单、一台设备、一位客户。应用里查对象、改对象，都在对象这一层。但对象的数据从哪来？

"Funnel reads data from Foundry datasources (such as datasets, restricted views, and streaming datasources)…" — Palantir Docs · Ontology architecture

Funnel 把这些数据索引进对象数据库，并在数据源更新时让索引保持最新[文档]。新一代的 Object Storage V2 默认对所有对象类型做增量索引[文档]。

比喻：数据集是仓库里的书，对象数据库是检索目录，Funnel 是编目员。新书入库，编目员把它登记进目录；读者查的是目录，不是直接去翻仓库。

由此有三个要点：

  • 对象跟着已提交的数据走。只有提交了新事务，才有新东西可索引。构建失败、事务被放弃，对象就不变。（由第 1、5 课推出）
  • 用户编辑落在对象层。Actions 服务负责把用户编辑应用到对象数据库[文档]，而不是在支撑数据集上提交事务。（"不在数据集上提交事务"是推论）
  • 回滚数据集要额外处理。如果数据集支撑的是 Object Storage V2 上的对象类型，回滚后"manual intervention is required"[文档]。目录不会自己知道仓库倒回了过去。

2. 判断练习（约 5 分钟）

每题描述支撑某个对象类型的数据集发生了什么，判断对象那边会怎样。四个选项每题都一样。

支撑数据集刚提交了一条 APPEND，加了 500 个新订单。

  1. 索引服务自动跟着更新对象
  2. 编辑直接写进对象数据库中
  3. 需要人工介入才能保持一致
  4. 对象不变，因为没有新事务
