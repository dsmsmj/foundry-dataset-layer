Foundry 数据集层 · 第 1 课 · 约 30 分钟

数据集 = 文件 + 事务 → 视图

学完这一课，给你任意一串事务历史，你能算出任意时间点数据集里"看得到"的是哪些文件。

文件→事务→视图→ 分支→构建→质量检查→Ontology→权限

这是你的使命里要画出的那条链路。本课打地基：前三环。后面每一环都建立在"视图"这个概念上。

1. 数据集只是一层包装

Foundry 的数据集里并没有"一张表"。它是一组文件外面的一层包装：

"Fundamentally, a dataset is a wrapper around a collection of files…" — Palantir Docs · Datasets

文件本身放在后端文件系统里（比如 HDFS 或 S3 这类云存储），Foundry 只记住"逻辑路径 → 物理路径"的映射[文档]。包装这一层负责的是：权限、schema、版本历史。

所以问题变成：既然底下就是一堆文件，"现在数据集里有什么"是怎么定义的？答案是事务。

数据集的文件实际存在哪里？

  1. 平台自带的关系数据库中
  2. 后端文件系统的目录下面
  3. 每个事务各自的压缩包里
  4. 计算引擎的内存缓存之中

2. 事务：数据集的"提交"

数据集里的文件只能通过事务（Transaction）改变。官方的类比是 Git：

"A transaction is analogous to a commit in Git: an atomic change…" — Palantir Docs · Transactions

一个事务有三种状态[文档]：

  • OPEN：正在往后端文件系统里写文件。
  • COMMITTED：提交成功，写入的文件生效。
  • ABORTED：放弃，期间写入的文件被忽略，就像没发生过。

四种事务类型

类型对视图做什么Git 里的直觉
SNAPSHOT用一组全新文件整体替换当前视图清空工作区后提交全部新文件
APPEND只加入新文件，不碰已有文件只新增文件的提交
UPDATE加入新文件，也可以覆盖已有文件的内容（A → A′）既新增又修改的提交
DELETE把文件从视图里移除删除文件的提交

定义逐条出自 Transaction types。

DELETE 有个容易踩的坑：它只是让文件不再出现在视图里，后端的物理文件还在。真正删除物理文件的是保留策略（Retention），那是另一套机制，后面再讲[文档]。

提交一个 DELETE 事务后，被删的文件会怎样？

  1. 立即从后端存储里永久擦除
  2. 移入回收站，七天后可恢复
  3. 从视图移除，物理文件仍在
  4. 只标记删除，下次构建清理

一个事务最终是 ABORTED，它写入的文件会怎样？

  1. 保留在视图里，等待重试
  2. 自动合并进下一个事务里
  3. 只在当前分支的视图中可见
  4. 被忽略，不进入任何视图

3. 视图：某一时刻"看得到"的文件

官方定义[文档]：视图（View）是数据集在某个分支、某个时间点上实际有效的文件内容。算法只有两步：

  1. 从该时间点之前最近的一个 SNAPSHOT 开始。
  2. 按顺序往后应用每个已提交的事务，跳过 ABORTED 的。

为什么从最近的 SNAPSHOT 开始？因为 SNAPSHOT 会整体替换视图，它之前发生的一切都不再影响结果。

官方例子

#事务之后的视图
1SNAPSHOT 写入 A、BAB
2APPEND 加入 CABC
3UPDATE 覆盖 A → A′A'BC
4DELETE 移除 BA'C

出自 Example of transaction types。如果之后再来一个只写入 D 的 SNAPSHOT，新视图就只有 D。

计算某个时间点的视图，应该从哪个事务开始往后回放？

  1. 最近一次整体替换的事务
  2. 时间点前最近的一个事务
  3. 最近一次覆盖文件的事务
  4. 数据集历史中第一个事务

4. 练习：预测视图

这是本课的核心练习。看事务历史，点选指定步骤之后视图里的文件，然后点"检查"。答错一次会给提示，第二次给出逐步回放。前 4 题是固定题，之后无限随机出题，建议至少连续做对 3 道随机题再结束。
