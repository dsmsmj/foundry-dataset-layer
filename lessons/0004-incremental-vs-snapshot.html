增量与快照：这次只算新的，还是从头算？

学完这一课，告诉你一个增量 transform 的输入上次运行后来了哪些新事务，你能说出这次它是增量跑、退回快照、构建失败，还是根本不跑。

文件→事务→视图→ 分支→构建→质量检查→Ontology→权限

还在"构建"这一环，往深走一层：第 3 课回答"跑不跑"，这一课回答"怎么跑"。

0. 热身：把前两课串起来

上游 clean_orders 被重算后，下游 order_facts 为什么也要重算？

  1. 它的代码也被改动了
  2. 所有数据集都会重算
  3. 上游会通知它去重算
  4. 它的输入有了新事务

在 feature 分支上构建，fallback 链是 feature → develop → master。某个输入只有 develop 和 master 分支，它读哪个？

  1. feature
  2. develop
  3. master
  4. 报错

顺带修正上次复述里的一个说法：变化是顺着依赖往下游传的，但构建不是一个接一个"串行"跑。互相没有依赖的 Job 会并行执行，只有存在依赖的 Job 才要等上游跑完[调研笔记 §5]。

1. 默认的 transform 每次都从头算

普通 transform 每次运行，都会读输入的全部数据，算完后整体替换输出。用第 1 课的话说，输出上提交的是一条 SNAPSHOT。

数据量小时这没问题。但想象一张每天追加几百万行的事件表：为了今天新来的那一点，把过去三年的数据全部重算一遍，太浪费了。

增量 transform 就是来解决这个的：它能查看自己上一次运行的信息，判断这次能不能只处理新增的部分；能就增量跑，不能就自动退回快照[文档]。

本课讲的是 Python 代码仓库里的增量 transform（@incremental() 装饰器）。Pipeline Builder 有自己的一套，原理相同。

2. 增量跑的时候，读到什么、写成什么

增量运行退回快照运行
输入默认读模式 added只有上次运行后新增的行输入的全部数据
输出默认写模式modify：追加到已有输出上replace：整体替换输出

出自 Incremental modes of inputs and outputs。另外还有 current（这次的全量输入）和 previous（上次运行时的全量输入）两种读模式，先知道有就行。

增量运行时，默认读模式 added 读到的是什么？

  1. 输入当前的全部数据
  2. 上次运行后新增的行
  3. 上次运行时的全部行
  4. 输出里已有的那些行

3. 什么时候不能增量

关键问题："只看新增的行"在什么时候是对的？只有输入是"只往后追加"的时候。一旦旧数据被换掉、改掉或删掉，光看新增部分就会算错。这正是第 1 课那四种事务的区别：

输入上的新事务能增量吗原因
APPEND✓只加新文件
UPDATE 只加新文件✓和追加一样
UPDATE 覆盖已有文件✗ 退回快照旧数据被改了
SNAPSHOT✗ 退回快照旧数据被整体换掉
DELETE 用户删除✗ 默认退回快照旧数据少了
DELETE 保留策略删除设了 allow_retention=True 才 ✓清理旧文件是常态，可以声明允许

此外两种情况一定是快照运行：输出从没构建过（第一次没有"上次"），以及 semantic_version 改了。这些规则都出自 Requirements for incremental computation。

为什么输入上来了一条 SNAPSHOT，增量 transform 就要退回快照？

  1. 快照文件格式不兼容
  2. 快照事务提交得太慢
  3. 无法只看新增的部分
  4. 增量只支持一个输入

四个开关

semantic_version默认 1。改它会强制下一次非增量运行。改了逻辑、需要把历史数据重算一遍时用。
require_incremental=True不能增量时直接失败，而不是悄悄退回快照。第一次构建和改了 semantic_version 时仍允许快照。
allow_retention=True允许保留策略删除输入/输出里的文件而不破坏增量。
snapshot_inputs把某些输入声明为快照输入：它们被整体重写也不影响增量。适合小的维表，比如地区对照表。

四条都出自 Incremental decorator。

为什么会有人想要 require_incremental？因为对大表来说，悄悄退回快照可能意味着一次几小时的全量重算。宁可让构建失败、让人来看一眼。
