提交一个 DELETE 事务之后，下面哪个说法对？

  1. 历史里多了一条新事务
  2. 历史里被删掉一条事务
  3. 物理文件被立刻擦除了
  4. 视图回退到上一个快照

记住这一层区分：事务是历史记录，只增不减；文件是事务写进去的东西；视图是按事务回放出来的结果。这一课里还会用到它。

1. 分支就是一个指针

第 1 课说过，视图是数据集在"某个分支、某个时间点"上的文件集合。现在来看"分支"是什么。

"…dataset branches are simply a pointer to the most recent transaction on that branch." — Palantir Docs · Branching

和 Git 一样：分支本身不存数据，只是指向这条线上最新的那个事务。每个分支都有一个父分支，只有根分支（通常叫 master）没有[文档]。子分支可以从另一个分支创建，也可以从任意一个事务创建。

develop 从 T2 分出。develop 上的视图回放 T1 → T2 → T4；master 上的视图回放 T1 → T2 → T3。

所以同一个数据集，在不同分支上可以有不同的视图。在 develop 上随便折腾，master 的视图不受影响。

删除分支

删除一个分支，删掉的只是指针，分支上的事务一条都不会删；如果它有子分支，子分支会改挂到它的父分支下面[文档]。和上面的热身题是同一个道理：事务只增不减。

删除一个数据集分支后会发生什么？

  1. 指针和事务都被一起删除
  2. 事务并入父分支后再删除
  3. 只删指针，事务仍然保留
  4. 子分支也会被级联删除掉

和 Git 最大的不同：不能合并

"Unlike Git, there is no support for merging dataset branches." — Palantir Docs · Branching

那在 develop 上验证好的东西怎么进 master？合并的是代码，不是数据：把代码仓库里的转换逻辑合进 master，再在 master 上重新构建，产出 master 自己的事务[调研笔记 §3]。

develop 分支上验证好的结果，怎样进入 master？

  1. 把数据分支合并进主分支
  2. 合并代码后在主分支重建
  3. 把事务复制粘贴到主分支
  4. 主分支自动同步开发分支

2. 构建时的 fallback 链

新开一个 feature 分支时，大部分数据集上还没有这个分支。那在 feature 上跑构建，输入读什么？逻辑用哪份？答案是 fallback 链：构建时指定一串分支，比如 feature → develop → master，找不到就往后退[文档]。

这里先认识一个新词：JobSpec 是"某个输出怎么算出来"的说明，包括它的输入和转换逻辑。在代码仓库的某个分支上提交代码，会把 JobSpec 发布到同名分支上[调研笔记 §3、§5]。下一课讲构建时会细说。

要解析的东西规则
JobSpec构建分支上有就用；没有就沿 fallback 链找第一个发布了 JobSpec 的分支
输入构建分支上有就读；没有就读 fallback 链里第一个存在的分支
输出新事务总是开在构建分支上。分支不存在时，从 fallback 链的第一个分支创建；没有 fallback 就作为根分支创建

再加两条保证，原文都很短[文档]：

  • 构建只改构建分支，绝不动其他分支。
  • 构建不会在输入数据集上创建分支。输入缺分支就往后退着读，不会替它建一个。

这两条保证就是分支有用的原因：你在 feature 上怎么构建，master 上的数据都安然无恙。
